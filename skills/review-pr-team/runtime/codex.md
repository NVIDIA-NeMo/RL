# Codex runtime

**Mandatory execution order:** Complete every applicable required step in the specified order; do not silently skip, abbreviate, sample, replace or waive it, cross its gate without evidence, or claim completion and explain an omission afterward; if a required step is blocked, identify it and keep dependent work pending unless the user explicitly authorizes a deviation or a higher-priority instruction requires it.

Read this file when running the shared review workflow in Codex. Claude Code follows [SKILL.md](../SKILL.md) as written. The Claude teams flag, tmux panes, native shared task tools, and Claude shutdown messages are not Codex prerequisites.

For Codex, this adapter overrides conflicting instructions in the shared phases, role templates and posting audits. Apply the tool mapping, role adaptations and review checks below when preparing agent prompts; retain the remaining shared review criteria and approval gates.

## Tool mapping

Use the collaboration tools actually exposed in the session. In environments where they are under the `collaboration` namespace, call them directly rather than through a shell or `functions.exec`.

| Shared workflow label | Codex operation |
| --- | --- |
| `Agent` with a named role | `collaboration.spawn_agent(task_name=..., message=...)` |
| `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, `blockedBy` | Leader-owned task ledger; `list_agents` supplies agent status, not task completion evidence |
| `SendMessage` to a running agent | `collaboration.send_message(target=..., message=...)` |
| `SendMessage` to resume a completed agent | `collaboration.followup_task(target=..., message=...)`; a plain message does not start a new turn |
| Wait for a report | `collaboration.wait_agent`, then inspect delivered messages/reports; the wait result is only a notification |
| `TaskStop` or stop redundant work | `collaboration.interrupt_agent(target=...)`; record the unfinished task as stopped |
| `AskUserQuestion` | Available user-input tool, or a concise question in chat; approvals use the runtime's real approval mechanism |
| `Read`, `Glob`, `Grep`, `Bash`, `WebFetch` | Available file, `rg`, shell, and web tools |

Agents can message peers or the leader with `send_message` using the canonical agent name supplied by the runtime. Share the role-to-agent mapping with them; `team-lead` in shared prompt examples means the actual parent (normally `/root`). Final reports are delivered to the parent in this runtime, including follow-up turns. For verdicts and peer challenges, explicitly send the full result as well; do not transfer Claude's claim that a resumed agent's final text is always lost. Deduplicate repeated deliveries by task ID and report revision.

## Codex review checks

Apply these checks to changed behavior and its related declarations, explanations and tests, including unchanged files. Keep the scope tied to the PR.

- **`rl-expert`:** trace changed options/backends through their owning schema (including inherited fields), validation and consumers; compare sibling declarations and adjacent error remedies with the newly accepted/rejected combinations. Check added, modified and related existing docstrings, comments, design flows and extension examples. Follow user-guide links to verify that target tables/examples include the promised backend or combination. For resource explanations, identify the executing process and allocator/stream/communicator owner and compare them with the text's subject. Missing new docstrings do not replace these checks.
- **`test-agent`:** for each changed branch or cross-backend call contract, identify the setup that reaches it and the assertion that would detect wrong or skipped behavior. Check mocks against the signature, attributes and return shape production actually inspects; verify library behavior from source/docs before flagging it. Distinguish matching implementations today from tests guarding their shared contract; an accepted parameter name alone does not validate payload contents. Search existing coverage before proposing another guard.
- **Coverage decisions:** distinguish unit, real-model, distributed, manual-run and recurring CI/nightly evidence where relevant. A broader test can reduce impact without making an ineffective local mock correct; a successful manual run does not establish recurring coverage. Keep discretionary test-matrix expansion a recommendation, separate from an unmet author request.
- **`comment-reviewer` and discovering agents:** match historical requests by concrete claim, target and requested edit. Preserve user-removed drafts; their disappearance is neither a code fix nor permission to restore them, and it does not exempt other locations or distinct issues. Record concrete excluded candidates with their specific evidence and reason. An existing-test exclusion needs its setup and detecting assertion; a duplicate exclusion needs the matching request's scope.
- **`devil-advocate`:** override the shared file-list disqualifier: an unchanged schema, diagnostic, test or document can require an update because of this PR. Require links to both the PR change creating that obligation and the missed update, and compare base/head to distinguish unrelated pre-existing defects. File-list absence alone does not establish a stale diff.
- **Leader and `devil-advocate`:** use the completion evidence below to distinguish discovery, verification and filtering. DA independently verifies the cited source and exclusions, including no-findings reports; omitted candidates receive peer verification and adversarial verdicts before editing. Keep these records internal.

## Discovery and completion evidence

For each changed behavior within a role's scope, record the affected contract, concrete source evidence, result (finding, checked with no issue, excluded with reason, or not applicable with reason), and actual execution status. Group related checks; a row per symbol or a fixed number of findings is not required. Use the following connections where the change makes them relevant:

- **Defaults and fallbacks:** When a change wraps, replaces or configures existing behavior, compare the base, head and pinned upstream behavior for both explicit inputs and omitted inputs. Trace defaults and fallbacks through configuration/environment lookup, normalization and the final consumer. Distinguish unset, empty, None and false where the implementation treats them differently. Tests or source checks using explicit overrides do not establish compatibility of the default path.
- **Behavior to explanations:** For each changed contract, use its concrete option, environment variable, API and dependency names to locate related docstrings, comments, diagnostics, design documents, support guides, READMEs and examples, including unchanged files. Read their relevant context and verify the specific claims about results, mechanisms, ownership, defaults, fallback behavior and dependency provenance against current source. Correct runtime behavior does not establish that its explanation is correct. After a named passage is fixed, check other passages making the same affected claim; searches locate evidence but do not replace reading it.
- **Work to observability:** when the PR compares the cost of a new processing stage, check which stage and population the existing metrics count and whether the new work reaches a logged metric. A missing metric is distinct from an already-requested benchmark or learning curve.
- **Claims to assumptions:** check numerical estimates and reference comparisons against batching/chunk boundaries, masks, denominators and the pinned reference's defaults and consumers. State the conditions under which a comparison holds; an estimate is not a measured result.
- **Copies to owners:** identify the defining declaration and all dependent producers/readers for copied formats, field names and values. Another module or schema in this repository is an owner too. Compare typed construction with handwritten payloads and the nearest sibling before dismissing a copy as repository-owned.

A file/member inventory, successful CI, resolved thread or completed agent report does not establish these checks. Before editing comments, the leader and DA must reconcile the evidence records with the changed behaviors; return unread or unexamined applicable checks to their owner and finish them. Do not describe a category as clean while its checks remain incomplete.

Owning specialists must identify the default/fallback paths and affected explanatory claims in their existing evidence records, with concrete inputs or passages, verifying source and outcome. Related cases may share a record; naming a file or saying "docs checked" is insufficient. DA must independently verify these dimensions, including source-backed no-findings conclusions, rather than repeating only API and runtime checks. Before comment editing, the leader must return any applicable but unexamined path or claim to its owner. Keep runtime behavior, default compatibility and explanation accuracy as separate conclusions; a clean result in one does not establish the others.

Keep independent claims separate during adjudication. Refuting a proposed crash or race does not refute a confirmed schema-contract or documentation mismatch at the same location. Record factual confidence separately from impact, apply the existing retention rules to the remaining claim, and show filtered candidates where those rules require it. Do not invent a runtime failure to justify a contract finding. Preserve explicit user exclusions rather than restoring declined comments.

## Independent discovery before challenges

Use one independent DA agent for two passes, both after Wave 1 has reported. This replaces the shared immediate full-findings handoff in Codex:

1. **Discovery:** spawn DA with `fork_turns="none"` (or the runtime's equivalent isolated context). Supply the applicable instructions, review scope, raw PR description/discussions/diff, source location, pinned revisions and execution restrictions. Withhold Wave 1 reports and any leader-provided candidate list, suspected locations, verdicts or exclusion records. DA reads the artifacts and independently identifies affected contracts, potential omissions and source-backed clean results, then reports them to the leader. Do not treat this report as completion of the adversarial task.
2. **Challenges:** after receiving the discovery report, send the same agent the complete Wave 1 findings, applicable check records, concrete exclusions and leader candidates. Use `followup_task` if it has completed its turn. DA reconciles both sets, checks the evidence and exclusions, and gives a verdict for every candidate, including its own discoveries. Have the owning specialist independently verify new DA candidates before editing comments. Record both passes in the task ledger; adjudication is incomplete until the combined set and any missing checks are resolved.

Do not use an inherited full-history context for the first pass: telling an agent to ignore findings it has already seen does not make discovery independent. A no-findings result still needs source evidence for the applicable checks. This adds no agent role and does not change the comment-editor or posting approval gates.

Where execution is permitted and available, run proposed tests before claiming they pass; otherwise report the statically established gap and a plan or example labelled not run.

## Task ledger and scheduling

Record task ID, role, dependencies, status, agent ID/name, report location or received content, and unresolved questions. A small leader-maintained table is enough; persist it only when session/handoff instructions require that. Task states are queued, running, reported, or deliberately stopped. Mark a task reported only after receiving its substantive report, including an explicit no-findings report where applicable.

Read the session's actual concurrency limit. With four slots including the leader, schedule at most three children at once. Reuse completed agents through `followup_task` for queued specialist roles when necessary. Keep logical role counts separate from the actual agent count; the preview and review body must describe the team that really ran.

Preserve these dependencies regardless of capacity:

1. Run every applicable Wave 1 role, collecting each report. Queue roles that do not fit, rather than omitting them or starting waiting agents in scarce slots.
2. Check the Codex review records and concrete exclusion reasons before marking Wave 1 reported; return unexamined applicable checks to their owner. Start an independent `devil-advocate` agent with only the discovery-pass inputs described above. Reserve an agent for both passes if the runtime limits total agents as well as active agents.
3. Receive DA's independent discovery report, then deliver the complete Wave 1 set, leader candidates, check records and exclusions for its challenge pass. Reconcile every commissioned adversarial report. For a challenge to a completed specialist, use `followup_task` with the challenge and evidence; forward its answer to DA. The leader brokers messages if peers cannot communicate directly.
4. Only after both DA passes and the completion-evidence checks are finished, dispatch `edit-comments` with the final survivors and body draft. A completed DA agent may take the editor role in a separate turn if capacity requires reuse. The leader may not replace the editor pass with its own prose.
5. Offer staging only after the ledger shows every required report received and all outstanding passes reported or deliberately stopped. An interrupted DA or editor task is incomplete; complete that role before opening its gate.

Use event waits of at most 60 seconds per call so progress updates remain possible. If delivery stalls, inspect status and ask the agent for an explicit full report; use `followup_task` when it has completed. Do not infer a verdict from silence, keep spawning duplicate passes indefinitely, or treat a status check as evidence.

The shared workflow's exception allowing continuation after a failed DA nudge does not apply in Codex. Collect the DA verdicts before presenting findings for staging or posting a review. If recovery fails, report the incomplete pass; the hard gate remains closed.

## GitHub transport

Discover installed GitHub tools first and prefer them when they provide the needed read/write operation. Otherwise check for `gh`. The shared `gh` examples are conveniences, not a dependency. Without `gh`, use an authenticated HTTP client such as Python `urllib.request` or `curl` against `https://api.github.com`:

| Shared example | HTTP equivalent |
| --- | --- |
| `gh pr view N` | `GET /repos/NVIDIA-NeMo/RL/pulls/N`; map `base.ref`, `base.sha`, `head.ref`, `head.sha`, `user.login`, and body/title |
| PR changed files | Paginated `GET /repos/NVIDIA-NeMo/RL/pulls/N/files` |
| PR commits | Paginated `GET /repos/NVIDIA-NeMo/RL/pulls/N/commits` |
| PR diff | `GET /repos/NVIDIA-NeMo/RL/pulls/N` with `Accept: application/vnd.github.diff`, or local merge-base/head diff |
| PR conversation/reviews | Paginated `GET /repos/NVIDIA-NeMo/RL/issues/N/comments`, `/pulls/N/reviews`, and `/pulls/N/comments` under the repo |
| Linked issue | `GET /repos/NVIDIA-NeMo/RL/issues/N` plus its paginated comments |
| `gh api PATH --method POST --input payload.json` | `POST /PATH` with the same JSON body |
| `gh api graphql --input payload.json` | `POST /graphql` with the same query/variables JSON |

Use GraphQL to obtain `mergeable`/`mergeStateStatus`, review requests, full review threads, and pending-review comment counts as required by the shared phases. Follow pagination; do not silently review only the first page. Use the current checkout's credential setup in the same shell, without printing credentials. Generate request bodies with `json.dump` and submit files/structured arguments; do not expand markdown or credentials through shell interpolation. Use a unique temporary directory for the review rather than shared `/tmp/q.json` filenames.

The approval gates apply equally to connectors and HTTP clients: the review request authorizes reading, not posting messages. Show the reviewed draft before creating a pending review, then get separate explicit approval before publishing. Do not overwrite an existing user-owned pending review to make room for yours.

## Teardown

Collect reports first. Inspect `list_agents`, then interrupt any still-running work that is no longer needed with `interrupt_agent`. Completed agents need no Claude shutdown message. Report any incomplete required role honestly; teardown does not turn an interrupted pass into a completed review. Preserve pending drafts, user changes, and any required handoff record.
