# Codex runtime

Read this file when running the shared review workflow in Codex. Claude Code follows [SKILL.md](../SKILL.md) as written. The Claude teams flag, tmux panes, native shared task tools, and Claude shutdown messages are not Codex prerequisites.

For Codex, this adapter overrides conflicting runtime mechanics in the shared phases and role templates. Keep the review criteria shared; apply the tool mapping and role adaptations below when preparing each agent's prompt.

## Tool mapping

Use the collaboration tools actually exposed in the session. In environments where they are under the `collaboration` namespace, call them directly rather than through a shell or `functions.exec`.

| Shared workflow label | Codex operation |
| --- | --- |
| `Agent` with a named role | `collaboration.spawn_agent(task_name=..., message=...)` |
| `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, `blockedBy` | Leader-owned task ledger; `list_agents` supplies agent status, not task completion evidence |
| `SendMessage` to a running agent | `collaboration.send_message(target=..., message=...)` |
| `SendMessage` to resume a completed agent | `collaboration.followup_task(target=..., message=...)`; a plain message does not start a new turn |
| Wait for a report | `collaboration.wait_agent`, then inspect delivered messages/reports; the wait result is only a notification |
| `TaskStop` or stop redundant work | `collaboration.interrupt_agent(target=...)`; record the unfinished task as stopped |
| `AskUserQuestion` | Available user-input tool, or a concise question in chat; approvals use the runtime's real approval mechanism |
| `Read`, `Glob`, `Grep`, `Bash`, `WebFetch` | Available file, `rg`, shell, and web tools |

Agents can message peers or the leader with `send_message` using the canonical agent name supplied by the runtime. Share the role-to-agent mapping with them; `team-lead` in shared prompt examples means the actual parent (normally `/root`). Final reports are delivered to the parent in this runtime, including follow-up turns. For verdicts and peer challenges, explicitly send the full result as well; do not transfer Claude's claim that a resumed agent's final text is always lost. Deduplicate repeated deliveries by task ID and report revision.

## Context and permissions

- Read applicable `AGENTS.md` instructions. Discover shared skills in `skills/` (also exposed through `.agents/skills`); do not require `.claude` configuration.
- The review memory is `~/.codex/review-memory/RL`. Read applicable Codex review rules and memory when present; do not write Claude's personal memory files.
- Use `_Generated by Codex_` as the review attribution.
- Follow the current sandbox and escalation mechanism. Do not pass Claude-only sandbox flags or request a blanket bypass.
- Pass the actual review worktree path, pinned base/head and submodule SHAs, initial working-tree status, local test/lint restrictions, and runtime mapping to each agent. A full-history fork may supply context, but do not rely on it to convey the assigned role and output requirements.

## Preparing role prompts

Before dispatch, translate the common preamble and assigned role template using this adapter. Include the applicable adaptations in the dispatched prompt so agents receive consistent executable instructions:

- **All roles:** work on the role/task supplied by the leader and report its ID and outcome. Replace native shared-task instructions with the leader-owned ledger/reporting process and map tool names using the table above. Apply the Codex context and permissions above instead of Claude-specific paths and settings.
- **`devil-advocate`:** the leader starts this task only after every Wave 1 report has arrived, with the complete findings attached to the dispatch. Begin reviewing that handoff immediately; do not wait for a separate wake-up message. If the handoff is missing, request it from the leader.
- **`test-agent` and any role doing runtime validation:** user and host restrictions override the shared local test-execution instructions, including GPU work and collect-only. When execution is prohibited or unavailable, report evidence-backed coverage gaps and a proposed test plan, explicitly marked as not run. Do not present unexecuted test code as a verified suggestion or claim it passes.

## Task ledger and scheduling

Record task ID, role, dependencies, status, agent ID/name, report location or received content, and unresolved questions. A small leader-maintained table is enough; persist it only when session/handoff instructions require that. Task states are queued, running, reported, or deliberately stopped. Mark a task reported only after receiving its substantive report, including an explicit no-findings report where applicable.

Read the session's actual concurrency limit; do not hardcode eight simultaneous agents. With four slots including the leader, schedule at most three children at once. Reuse completed agents through `followup_task` for queued specialist roles when necessary. Keep logical role counts separate from the actual agent count; the preview and review body must describe the team that really ran.

Preserve these dependencies regardless of capacity:

1. Run every applicable Wave 1 role, collecting each report. Queue roles that do not fit, rather than omitting them or starting waiting agents in scarce slots.
2. Assign the complete Wave 1 set (including leader candidates) to an independent `devil-advocate` agent that did not produce those findings. Reserve an agent for this pass if the runtime limits total agents as well as active agents.
3. Reconcile every commissioned adversarial report. For a challenge to a completed specialist, use `followup_task` with the challenge and evidence; forward its answer to DA. The leader brokers messages if peers cannot communicate directly.
4. Only then dispatch `edit-comments` with the final survivors and body draft. A completed DA agent may take the editor role in a separate turn if capacity requires reuse. The leader may not replace the editor pass with its own prose.
5. Offer staging only after the ledger shows every required report received and all outstanding passes reported or deliberately stopped. An interrupted DA or editor task is incomplete; complete that role before opening its gate.

Use event waits of at most 60 seconds per call so progress updates remain possible. If delivery stalls, inspect status and ask the agent for an explicit full report; use `followup_task` when it has completed. Do not infer a verdict from silence, keep spawning duplicate passes indefinitely, or treat a status check as evidence.

The shared workflow's exception allowing continuation after a failed DA nudge does not apply in Codex. Collect the DA verdicts before presenting findings for staging or posting a review. If recovery fails, report the incomplete pass; the hard gate remains closed.

## GitHub transport

Discover installed GitHub tools first and prefer them when they provide the needed read/write operation. Otherwise check for `gh`. The shared `gh` examples are conveniences, not a dependency. Without `gh`, use an authenticated HTTP client such as Python `urllib.request` or `curl` against `https://api.github.com`:

| Shared example | HTTP equivalent |
| --- | --- |
| `gh pr view N` | `GET /repos/NVIDIA-NeMo/RL/pulls/N`; map `base.ref`, `base.sha`, `head.ref`, `head.sha`, `user.login`, and body/title |
| PR changed files | Paginated `GET /repos/NVIDIA-NeMo/RL/pulls/N/files` |
| PR commits | Paginated `GET /repos/NVIDIA-NeMo/RL/pulls/N/commits` |
| PR diff | `GET /repos/NVIDIA-NeMo/RL/pulls/N` with `Accept: application/vnd.github.diff`, or local merge-base/head diff |
| PR conversation/reviews | Paginated `GET /repos/NVIDIA-NeMo/RL/issues/N/comments`, `/pulls/N/reviews`, and `/pulls/N/comments` under the repo |
| Linked issue | `GET /repos/NVIDIA-NeMo/RL/issues/N` plus its paginated comments |
| `gh api PATH --method POST --input payload.json` | `POST /PATH` with the same JSON body |
| `gh api graphql --input payload.json` | `POST /graphql` with the same query/variables JSON |

Use GraphQL to obtain `mergeable`/`mergeStateStatus`, review requests, full review threads, and pending-review comment counts as required by the shared phases. Follow pagination; do not silently review only the first page. Use the current checkout's credential setup in the same shell, without printing credentials. Generate request bodies with `json.dump` and submit files/structured arguments; do not expand markdown or credentials through shell interpolation. Use a unique temporary directory for the review rather than shared `/tmp/q.json` filenames.

The approval gates apply equally to connectors and HTTP clients: the review request authorizes reading, not posting messages. Show the reviewed draft before creating a pending review, then get separate explicit approval before publishing. Do not overwrite an existing user-owned pending review to make room for yours.

## Teardown

Collect reports first. Inspect `list_agents`, then interrupt any still-running work that is no longer needed with `interrupt_agent`. Completed agents need no Claude shutdown message. Report any incomplete required role honestly; teardown does not turn an interrupted pass into a completed review. Preserve pending drafts, user changes, and any required handoff record.
