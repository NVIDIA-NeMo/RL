# Reuse and precedent

Use what the repo already has before adding something new.

- **Before adding a helper, util, mechanism, config switch, CI lane or CI step, grep the repo for an existing one and use it instead of writing a new set.** A new mode/backend/transport goes into the existing selector, not a new boolean elsewhere, and a fixed `Literal` of roles should be a name → cluster map (#2971, #4465); a binary the image installs is tested by a unit test in the existing lane, not a new CI step (#4375). Do not merge two things that only look alike: if they change for different reasons, prefer duplication over the wrong abstraction. Review Details: [new-option-check-existing-selector](../../review-pr-team/references/details/new-option-check-existing-selector.md), [check-in-the-image-ci-already-builds](../../review-pr-team/references/details/check-in-the-image-ci-already-builds.md).
- **A mechanism with no precedent in the repo should first try the existing way.** Settle "is there precedent" with a `git grep` on `origin/main`, not from memory. Adopt the new way only when the existing one does not work. (#3613) Review Details: [no-precedent-try-the-existing-way](../../review-pr-team/references/details/no-precedent-try-the-existing-way.md).
- **Follow the nearest sibling. A new component that parallels an existing one (a new worker group ↔ `lm_policy.py`, a new advantage estimator ↔ the existing estimators, a new config block ↔ `MasterConfig`) follows its pattern: backend dispatch, override hooks (e.g. `resolve_policy_worker_cls`), guards/validation, type annotations, and return-shape consistency; new files and tests follow their siblings' location and shape.** "It works for the shipped recipe" is not enough if the new component silently diverges from its sibling's contract. A runtime vLLM patch goes in `patches.py` and its tests in `test_vllm_patches.py`, not a new module (#3286, #4820).
