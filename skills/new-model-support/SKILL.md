# New model support (AutoModel + vLLM)

Goal: a model released by its lab runs GRPO end to end in NeMo-RL, with the policy trained by AutoModel (DTensor, FSDP2 + EP) and rollouts generated by vLLM, and ships with a recipe and a model guide whose claims are backed by a run. The workflow front-loads cheap checks on a proxy model so that the expensive full-model runs only find problems that need full scale.

## Scope

- In scope: AutoModel training backend, vLLM generation, colocated and non-colocated layouts, BF16 training. Text-only paths of multimodal checkpoints are in scope; multimodal RL is a separate validation.
- Out of scope: the Megatron / MCore backend (use Megatron-Bridge's `adding-model-support` and `nemo-rl-e2e-testing` skills); post-support enhancements such as FP8, context parallel for long sequences, or speculative decoding; bitwise train-inference consistency (Automodel's `train-inference-consistency` skill; the bar here is `gen_kl_error` around `1e-3`, not zero differing bytes).

## Who owns what

A new model touches three code bases. NeMo-RL owns only the last row. During a bring-up, faults in AutoModel or vLLM are fixed on per-model branches rather than waited for upstream; see [branches-and-upstreaming.md](branches-and-upstreaming.md).

| Layer | Owner | Decides | Evidence it provides |
|---|---|---|---|
| Training model definition: modules, HF state-dict adapter, parallel plans, precision policy | AutoModel (`nemo_automodel/components/models/<model>/`) | what the trainer computes | the model PR's validation section: logits KL against the official or HF reference on the first released layers, SFT loss curves, CP/EP parity |
| Inference model and kernels | vLLM (`vllm/model_executor/models/<model>.py`) | what the rollout computes | the vLLM support PR; usually no comparison against AutoModel |
| RL integration: dependency pins, config loading, architecture registration, weight refit, recipe, guide | NeMo-RL | that the two meet on the same weights | `gen_kl_error`, refit logs, the GRPO runs in this skill |

Nobody upstream compares AutoModel against vLLM's native implementation, and nobody exercises the refit path. Those two gaps are what this skill validates. AutoModel's checkpoint vLLM-deploy CI test compares greedy tokens through vLLM's Transformers backend, not the native kernels, so it does not close either gap.

## Stages and gates

Do not start a stage until the previous gate passes. Record each gate result with the code commit, image, config and job id that produced it.

Open the stage's file (the Read column) at the start of every stage, even if it was skimmed earlier in the session. Each file lists failures already solved in past bring-ups, with their fixes; in one bring-up, two OOMs documented in the stage-3 file cost about two hours because the file was opened only after the long run crashed.

| # | Stage | Gate to pass | Read |
|---|---|---|---|
| 1 | Dependencies and image | AutoModel and vLLM pinned to commits that support the model; `uv lock` resolves; image built; the AutoModel model class loads the checkpoint config; vLLM generates coherent text from the real checkpoint on its own (for a model too large for the proxy's nodes, this check moves to the start of stage 3) | [deps-and-image.md](deps-and-image.md) |
| 2 | Proxy enablement | On a layer-sliced proxy of the real checkpoint: GRPO runs 1 to 2 steps end to end (generation, refit, logprobs, train step), checkpoint save and resume work, `gen_kl_error` is finite, flat across steps and below the triage threshold | [proxy-and-enablement.md](proxy-and-enablement.md) |
| 3 | Full-model short run | The real model at the target topology runs several GRPO steps without OOM or hang, saves one checkpoint and resumes from it; `gen_kl_error` around `1e-3`; refit time and step time recorded | [full-model-and-longrun.md](full-model-and-longrun.md#full-model-short-run) |
| 4 | Long run | 100 or more GRPO steps with no crash in the RL loop; `gen_kl_error` stays around `1e-3` with no upward trend; reward and validation accuracy improve | [full-model-and-longrun.md](full-model-and-longrun.md#long-run-validation) |
| 5 | Document and announce | Recipe matches the validated run; model guide on the support branch with support status, environment, launch, reference curves and known issues; README news entry links the branch | [docs-and-release.md](docs-and-release.md), [branches-and-upstreaming.md](branches-and-upstreaming.md#announce-from-the-branch) |

Merging the support into NeMo-RL `main` is not a stage of the bring-up: it waits for NeMo-RL's next AutoModel bump ([merge into main later](branches-and-upstreaming.md#merge-into-main-later)).

Three-way alignment (reference vs AutoModel vs vLLM) is not a fixed stage. Enter [mismatch-triage.md](mismatch-triage.md) from any stage when `gen_kl_error` misses its gate.

Support status is reported in two levels: **Functionally Ready** after stage 4 has passed at least once, **Long-Run Convergence Validated** after a full-length run with a healthy and reproducible reward curve.

## Rules that hold everywhere

- Pin vLLM and AutoModel to exact commits (a commit wheel for vLLM, a submodule commit for AutoModel). A floating nightly can change the internal APIs that refit depends on between two runs.
- A gate passes on a run, not on a code read. A metric that is absent, or zero because nothing produced it, is not evidence; confirm the producer ran (log line, step count) before trusting it.
- Never change the recipe to make a gate pass silently: if a sequence length, batch size or precision is reduced to get through, the guide states it as the validated scope.
- MoE models run with rollout routing replay (R3, `policy.router_replay.enabled: true`) from the first proxy smoke onward, and the recipe ships with it on. Turning it off is the exception and is stated in the guide.
- Separate generic fixes from model-specific ones. Generic fixes (refit dtype, memory, config loading) are gated by configuration or by capability checks, not by model name. Model-specific code is named after the model and installed only when the model's config asks for it.
- During bring-up the evidence for a fix is the proxy end-to-end GRPO run, not unit tests. Do not run the full unit-test suite or write a unit test per fix: the support branch is per-model, so other models are not expected to keep working on it, and a unit test proves less than one proxy step. Unit tests belong to the later merge into main, when generic fixes are split out.
- Fix where the fault is, on that repository's per-model branch, one concern per commit, and add the change to the branch's change list. Do not open upstream issues or PRs automatically; a human checks and splits them ([record, do not file](branches-and-upstreaming.md#upstream-problems-record-do-not-file)).
- Work without waiting. Fixing code on the support branch, rerunning the proxy, resubmitting a job that failed inside the RL loop, and sizing the next run need no approval. Stop and ask a human only before actions visible outside the workspace (pushing a branch, opening a PR or issue, editing the README news on `main`) and before abandoning a counted long run.
- An approval to open a PR covers the NeMo-RL support branch only, as a draft. Never open a PR on AutoModel or vLLM: their changes stay on the dev branch and in the change list until a human proposes them.
- Report without being asked: when a gate passes, when a long job ends, and when a job fails for a reason outside the code (the scheduler cannot allocate the nodes, the cluster or storage fails). Do not keep resubmitting such a job; report it and wait.
- Training quality is not tuned during a bring-up. The recipe inherits its optimizer settings from an existing recipe ([recipe](proxy-and-enablement.md#smoke-run)); if reward and validation accuracy do not improve with them, stop and hand the run to a human.
- Every run records the code commit and dirty state, the image, the full config and the job id. Never write secrets into a logged command; export them as environment variables.
- A proxy proves plumbing and numerics paths, not quality: its reward and generation length are meaningless, and its `gen_kl_error` is compared with a known-good proxy run, not with the full model.

## Terms

| Term | Meaning |
|---|---|
| proxy | a layer slice of the released checkpoint that keeps every layer type and every non-decoder component; the daily development model |
| refit | transferring the policy's updated weights from the AutoModel workers into vLLM before each rollout |
| colocated | training and generation share the same GPUs and swap memory between phases |
| `gen_kl_error` | per-step KL between the rollout engine's logprobs and the trainer's recomputed logprobs on the same tokens and weights; the train-inference mismatch signal |
| reference | the lab's official inference implementation, or the HF modeling file when that is the published reference |
| support branch | the per-model NeMo-RL branch (and matching AutoModel dev branch) where a bring-up is developed and announced |
| change list | the list of every change a bring-up made, by repository and generic or model-specific; the input for the later merge into main |
| crash | any job that ends with an error in the RL loop; a scheduled time-limit stop followed by resume from checkpoint is not a crash |
