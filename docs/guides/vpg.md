# Version-Point Gradients for Async GRPO

Async GRPO trains on rollouts generated by an older policy. With a maximum trajectory age of `L`, a batch can come from weights `θ_g` that are up to `L` optimizer steps older than the current weights `θ_t`. The default path evaluates the GRPO loss at `θ_t` and corrects for the mismatch with token-level importance sampling (IS): `w = π_θt / π_θg`. When the policy moves quickly, the IS weights become heavy-tailed. The gradient estimate then has a very large variance, and training can collapse.

Version-point gradients (VPG) remove the importance weights instead of correcting them:

1. The trainer keeps a snapshot of the weights of every version a buffered batch can come from.
2. For each batch, it swaps the generating version `θ_g` into the model and runs the forward and backward pass there. The PPO ratio and the IS weight are 1 at that point.
3. It swaps the current weights back and applies the normal optimizer step to `θ_t` with that gradient.

The loss, the advantage estimator and the optimizer are unchanged. The lag becomes a plain gradient delay.

With bitwise trainer/generator parity (`policy.megatron_cfg.batch_invariant_mode`), the trainer's log-probs at `θ_g` equal the generator's log-probs bit for bit, so every IS weight is exactly 1. Without parity, VPG still works, but the IS weight is only approximately 1, within the trainer/generator numerical mismatch.

## When to Use It

- Use it for async GRPO with `max_trajectory_age_steps >= 1` when the IS weights become heavy-tailed. Signs of this are a growing `train/gen_kl_error`, `train/probs_ratio_max` far above 1, or a reward collapse that the synchronous or lag-1 run does not show.
- The trainer skips the current-weight log-prob pass after the first step; snapshots and parameter all-gathers add overhead.
- It does not fix instability that also appears without lag (for example, a learning rate that is too high for synchronous GRPO).

## Requirements

`grpo.async_grpo.version_point_gradient=true` is validated at startup. It requires:

- async GRPO with the in-process replay buffer (`data_plane.enabled=false`);
- the Megatron policy with the distributed optimizer, Megatron DDP (not Megatron-FSDP), pipeline parallel size 1, no optimizer CPU offload, no `overlap_param_gather_with_optimizer_step`, and BF16 parameters (no `fp8_param` or `fp4_param`), with training CUDA graphs disabled;
- non-colocated generation; whole-batch VPG requires `in_flight_weight_updates=false`, while tokenwise VPG supports in-flight refits with Megatron generation and KV recomputation;
- one optimizer step per rollout batch (`policy.train_global_batch_size` = prompts per step × generations per prompt);
- `policy.router_replay` disabled, `loss_fn.force_on_policy_ratio=false`, and importance sampling enabled for fallback steps.

`policy.megatron_cfg.batch_invariant_mode=true` is recommended. Without it a warning is printed.

## Configuration

```yaml
grpo:
  async_grpo:
    enabled: true
    max_trajectory_age_steps: 8
    in_flight_weight_updates: false
    version_point_gradient: true   # default: false
loss_fn:
  use_importance_sampling_correction: true   # used by steps that fall back to the IS path
```

A whole-batch VPG step falls back to the IS path at `θ_t` when its batch mixes generation versions or its version has no snapshot. Fallbacks are logged.

### Tokenwise version points

The runnable example is `examples/configs/recipes/llm/grpo-qwen3-8b-base-1n4g-megatron-async-vpg-tokenwise.yaml`. For rollouts that cross in-flight weight updates, enable:

```yaml
grpo:
  async_grpo:
    enabled: true
    version_point_gradient: true
    version_point_per_token: true
    in_flight_weight_updates: true
    recompute_kv_cache_after_weight_updates: true
policy:
  generation:
    backend: megatron
    mcore_generation_config:
      kv_cache_management_mode: recompute
```

| Setting | Purpose and supported values |
|---|---|
| `grpo.async_grpo.version_point_per_token` | Boolean, default `false`. Evaluate each loss token at its stamped behavior-weight version. Requires `version_point_gradient=true`. |

The Megatron extra’s `torch-memory-saver` dependency supplies stable KV pointers for recompute mode with inference CUDA graphs. The generator stamps tokens from the engine's policy-epoch boundaries. Before resuming after a refit, it installs the new epoch and recomputes the KV state under those weights. For each version in the batch, the trainer selects its rows and masks the loss to its tokens, truncating each prefix after the last selected token. These passes accumulate into the existing gradient buffers; the optimizer and scheduler step once at the restored current weights. DP padding rows carry zero token masks and sample weights. Each loss token contributes once to the global token denominator, and sequence counts include each original row once.

This mode requires text-only rollouts, token-level loss and importance ratios, CP=1, no sequence log-prob filtering or sequence-level IS masks, no KL-in-reward, and no positive-example NLL, MTP, draft, distillation or MoE auxiliary objectives. MoE token dropping, Sinkhorn routing and quantile-balancing routing are unsupported. The existing VPG requirements also apply. SingleController remains unsupported. A batch with an unknown token stamp or an evicted snapshot takes the ordinary IS path as a whole.

Cost grows with the number of behavior versions. Prefix activations from different weights cannot be shared exactly; prefix truncation and row selection reduce redundant work, while sequence packing or dynamic batching can reduce padding. This option changes the training path and is disabled in the six published paper-reproduction arms.

Snapshots are saved with every checkpoint under `<checkpoint>/policy/version_snapshots/` and restored on resume, so a resumed run keeps computing every buffered batch's gradient at its generation weights.

## Metrics

| Metric | Meaning |
|---|---|
| `train/version_point_applied` | 1 if the step's gradient was taken at the generation weights, 0 on the IS path |
| `train/version_point_age` | current version minus the batch's generation version |
| `train/version_point_mixed_batch` | 1 if the batch mixed generation versions; tokenwise VPG can handle it |
| `train/version_point_no_snapshot` | 1 if a required version had no snapshot (IS path) |
| `train/version_point_unstamped_tokens` | 1 if a tokenwise batch had unknown behavior stamps (IS path) |
| `train/version_point_num_versions` | Number of stamped behavior versions in a tokenwise batch |
| `train/version_point_parity` | max \|PPO ratio − 1\| over loss tokens on version-point steps; 0 under bitwise parity |
| `train/version_point_snapshot_gb` | host memory held by the snapshots per trainer rank (GB) |
| `timing/train/version_point_snapshot` | time to take the per-step snapshot |

`train/version_point_parity` is derived from `probs_ratio_min` / `probs_ratio_max` and needs the full loss metrics (not `metrics_level: minimal`).

## Memory and Checkpoint Cost

Each trainer rank keeps `L + 1` snapshots of its distributed-optimizer shard of the BF16 parameters:

- **Host (pinned) memory per rank:** `(L + 1) × 2 bytes × P_rank / DP`, where `P_rank` is the number of parameters on the rank after tensor/expert parallelism and `DP` is the data-parallel size. For Qwen3-8B with 2 trainer ranks (DP 2), one version is 8.2 GB per rank, so `L = 8` needs 74 GB per rank (148 GB per node).
- **GPU memory:** one extra copy of the rank's shard (8.2 GB for the 8B example) during the forward/backward pass.
- **Checkpoint size:** the same `(L + 1)` shards per rank are written to every checkpoint (148 GB for the 8B example at `L = 8`).
- **Time:** one snapshot (device-to-host copy of the shard) per step and two all-gathers of the parameters per training step. The trainer skips its log-prob pass at the current weights.

## Reproduce a Result

The recipe `examples/configs/recipes/llm/grpo-qwen3-8b-base-1n4g-megatron-async-vpg.yaml` trains Qwen3-8B-Base on MATH levels 3-5 (plain `User:/Assistant:` prompt, 16 prompts × 16 samples, validation on AIME 2024, AIME 2025 and MATH-500) with async GRPO at `max_trajectory_age_steps=8`, learning rate 1e-5, batch-invariant kernels and VPG on. It needs one node with 4 GPUs (2 trainer + 2 generation).

```sh
# VPG
HF_HUB_OFFLINE=0 uv run examples/run_grpo.py \
  --config examples/configs/recipes/llm/grpo-qwen3-8b-base-1n4g-megatron-async-vpg.yaml \
  grpo.seed=1 grpo.max_num_steps=80 \
  logger.log_dir=results/vpg_l8/logs checkpointing.checkpoint_dir=results/vpg_l8/ckpt

# IS baseline at the same lag
HF_HUB_OFFLINE=0 uv run examples/run_grpo.py \
  --config examples/configs/recipes/llm/grpo-qwen3-8b-base-1n4g-megatron-async-vpg.yaml \
  grpo.async_grpo.version_point_gradient=false \
  grpo.seed=1 grpo.max_num_steps=80 \
  logger.log_dir=results/is_l8/logs checkpointing.checkpoint_dir=results/is_l8/ckpt
```

For the six-arm Qwen3-30B-A3B BF16/NVFP4 comparison, including runtime provenance, startup gates, and portable launch scripts, see [the reproduction folder](https://github.com/NVIDIA-NeMo/RL/tree/main/examples/version_point_gradients). The 8B example above is a smaller, separate configuration.
