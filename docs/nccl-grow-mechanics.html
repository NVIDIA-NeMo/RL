NCCL communicator lifecycle

How NCCL Communicator Grow Works

A source-guided explanation of how existing ranks and newly added ranks rendezvous, exchange peer information, rebuild communication topology, and create a larger NCCL communicator.

NCCL 2.29+ ncclCommGrow Bootstrap + topology + transport NeMo-RL refit context
01 · Mental model

The UID is an entrance, not a topology database

A grow UID does not contain the full member list, GPU topology, ring layout, or transport connections. It is an opaque rendezvous handle that lets new ranks enter NCCL's bootstrap protocol.

Grow requires more than a UID: the grow UID, the target world size, an assigned rank for every new participant, the parent communicator on existing ranks, and concurrent participation from every rank.
1

Bootstrap plane

Establishes temporary reachability between all participants and creates a bootstrap ring for control-message exchange.

2

Topology plane

Exchanges GPU, host, process, NIC, and graph information, then computes rings, trees, channels, and rank mappings.

3

Data plane

Creates the P2P, shared-memory, NVLink, and network transports used by later NCCL collectives.

02 · Grow UID

What the UID contains—and what it does not

ncclCommGetUniqueId() creates an ncclBootstrapHandle. NCCL starts a temporary bootstrap root listener and copies its handle into the 128-byte opaque ncclUniqueId.

Conceptually included

  • Bootstrap root socket address
  • A grow-session magic value
  • The parent communicator size
  • Opaque bootstrap metadata

Not included

  • The complete rank membership list
  • GPU-to-GPU or GPU-to-NIC topology
  • Ring and tree layouts
  • Established transport connections

The UID is single-use. Once the grow operation succeeds, NCCL consumes it; the application must generate a new grow UID for a later expansion.

03 · Bootstrap stitching

How existing and new ranks become reachable

Existing ranks already have a parent bootstrap network. New ranks have only the grow UID. NCCL combines these two mechanisms to construct a new bootstrap ring spanning the expanded world.

Important distinction: the bootstrap ring only gives NCCL a way to move initialization messages among all ranks. The final collective rings and trees are computed later from discovered topology.
04 · Topology construction

NCCL does not retrieve topology; it rebuilds it

Once the expanded bootstrap network exists, every rank contributes information. NCCL all-gathers that information, discovers local hardware, computes communication graphs, exchanges graph proposals, and establishes the required transports.

  1. Collect peer identity and capability

    Each rank fills ncclPeerInfo with GPU, host, process, version, and transport capabilities. A bootstrap AllGather gives every rank the complete peer table.

  2. Discover local hardware topology

    Each process inspects its GPU, PCIe, NVLink/NVSwitch, CPU/NUMA, and NIC relationships, then computes viable local paths.

  3. Compute candidate communication graphs

    NCCL searches for ring, balanced-tree, CollNet, and NVLS layouts according to hardware capabilities and communicator settings.

  4. Exchange and reconcile graph information

    A later AllGather shares topology-rank and graph information so all participants derive compatible global channels and mappings.

  5. Create transport connections

    NCCL initializes the selected P2P, shared-memory, NVLink, and network endpoints. The resulting communicator becomes the data plane used by collectives.

06 · Concrete example

Growing a shrunk refit group from 1,022 to 1,024 ranks

Suppose a two-GPU generation instance was excluded by shrink and later recovers. The recovered processes join at the end of the current rank space; they do not reclaim their pre-shrink rank numbers.

Participant Input communicator Grow arguments Rank in new communicator
Existing grow root 1,022-rank parent grow(1024, uid) Preserves existing rank
Existing non-root 1,022-rank parent grow(1024) Preserves existing rank
Recovered GPU process A Null communicator grow(1024, uid, rank=1022) 1,022
Recovered GPU process B Null communicator grow(1024, uid, rank=1023) 1,023
NeMo-RL implication: all training and active generation workers must switch to the returned communicator before the next refit. A recovered worker using the new communicator cannot safely synchronize weights with peers still using the parent communicator.
07 · Ownership boundary

Application responsibilities versus NCCL responsibilities

Application / orchestration layer NCCL library
Detect that a generation instance recovered Create and manage the temporary bootstrap listener
Select one existing grow root Stitch existing and new ranks into a bootstrap ring
Generate and externally distribute UID bytes AllGather peer and graph information
Choose target world size and unique new rank IDs Discover local GPU, PCIe, NVLink, and NIC topology
Launch all grow calls concurrently Compute rings, trees, channels, and rank mappings
Quiesce refit traffic and coordinate communicator swap Create transport connections and return the new communicator
Retire the parent communicator when safe Consume the one-time grow UID

Operational invariants

  • All participants must use the same target world size.
  • New ranks must receive unique assigned ranks in the expanded range.
  • Existing ranks preserve their current communicator rank.
  • Grow is collective; participants must be launched concurrently.
  • A grow UID is bound to one grow attempt and cannot be reused.
  • No refit operation should mix parent and expanded communicators.
