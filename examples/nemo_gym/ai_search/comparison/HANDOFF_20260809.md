# AI-search 阶段性工作总结与测试结论

更新时间：2026-08-09

## 一句话结论

AI-search 训练链路和三方性能对比已经跑通。相同模型、数据、检索服务和
4×A100 硬件下，NeMo RL 每个训练 step 的墙钟时间最短；但它生成的内容也
更短，所以按端到端生成 token 吞吐计算，并没有领先 Search-R1 和 ZeroSearch。

目前最值得优化的不是搜索服务，而是 NeMo RL 每步训练后向 vLLM 同步新权重
的过程。

## 当前完成情况

已经完成以下工作：

- 在 NeMo RL 中实现了可训练的 AI-search GRPO 示例。
- 实现了统一的 `SearchProvider` 接口、E5 编码和 cuVS 检索后端。
- 支持异步检索批处理、结构化工具调用、答案与检索奖励、测试和使用文档。
- 将默认策略切换到 Qwen2.5-7B-Instruct，并在单张 B300 上完成全参数训练链路
  验证。
- 选择 Search-R1 和阿里 ZeroSearch 作为外部对照实现。
- 为三套实现补齐 generation、search、policy/reference logprob、reward、
  advantage、actor update、权重同步和 checkpoint 等计时点。
- 在同一台 4×A100-SXM4-80GB 节点上完成三套实现的统一训练和 profiling。
- 输出了完整性能报告和机器可读的逐 step 结果。

## 对齐后的测试条件

三套实现使用同一套实验条件：

| 项目 | 配置 |
| --- | --- |
| 模型 | `Qwen/Qwen2.5-3B-Instruct` |
| 精度与训练方式 | BF16、全参数 GRPO |
| 硬件 | 同一台 4×A100-SXM4-80GB 节点 |
| 训练数据 | 32 个训练问题、8 个验证问题 |
| 检索语料 | 同一份 160 篇文档的两跳合成语料 |
| 检索服务 | 同一个本地 BM25 服务，top-3 |
| 每个训练 step | 4 个问题 × 每题 4 条轨迹，共 16 条轨迹 |
| Agent 上限 | 最多 2 轮搜索，再进行 1 次只回答不搜索的生成 |
| 采样参数 | temperature 1.0、top-p 0.95、每轮最多 256 token |
| Reward | 归一化答案 exact match |
| 统计口径 | 第 1 个 step 预热，统计第 2–4 个 step 的平均值 |

为了保证口径一致，本轮还修正了两个容易造成误判的问题：

- Search-R1/ZeroSearch 原始训练循环存在计数差异，配置 4 个 step 时实际只会
  做 3 次参数更新；已修正为真正完成 4 次更新。
- ZeroSearch 原来会在最终回答阶段继续做一次没有必要的搜索；已改成最终阶段
  只回答，不再搜索。

## 训练性能结果

| 实现 | 平均 core step | 每条轨迹生成 token | Rollout token/s | E2E token/s |
| --- | ---: | ---: | ---: | ---: |
| NeMo RL AI-search | **16.94 s** | 82.06 | **450.74** | 77.54 |
| Search-R1 | 27.53 s | 140.35 | 87.27 | 81.83 |
| ZeroSearch | 28.77 s | 157.58 | 93.29 | **87.61** |

通俗地说：

- 如果只问“完成一次训练更新需要多久”，NeMo RL 最快，相比 Search-R1 快
  约 1.63 倍，相比 ZeroSearch 快约 1.70 倍。
- NeMo RL 的 rollout 生成效率明显更高，但每条轨迹生成得更短。
- 把实际生成 token 数考虑进去后，三套实现的端到端吞吐比较接近，ZeroSearch
  略高。
- 因此不能只拿 16.94 秒对比 27–29 秒，就断言 NeMo RL 的训练框架本身快了
  1.7 倍。

## 各实现的主要瓶颈

### NeMo RL

NeMo RL 平均 16.94 秒的 core step 中：

| 阶段 | 耗时 | 占比 |
| --- | ---: | ---: |
| 向 4 个 vLLM worker 同步新权重 | **7.45 s** | **44.0%** |
| Rollout generation | 2.94 s | 17.3% |
| 切换到训练状态及准备 batch | 2.37 s | 14.0% |
| Logprob 状态准备 | 1.67 s | 9.9% |
| Actor backward/optimizer | 1.44 s | 8.5% |
| Policy + reference logprob 计算 | 0.98 s | 5.8% |

结论：NeMo RL 下一步应优先优化权重同步和训练/推理状态切换。搜索、reward
和 advantage 的耗时都非常小，不值得优先投入。

### Search-R1 和 ZeroSearch

- Search-R1 的 generation/agent loop 占 93.7%。
- ZeroSearch 的 generation/agent loop 占 93.5%。
- 两者 actor backward/optimizer 都约为 1.4 秒。
- Search-R1 每 step 搜索约 31 毫秒，ZeroSearch 约 112 毫秒。

结论：两套 veRL 实现的主要问题是多轮生成速度。ZeroSearch 的单请求检索方式
可以继续做批处理优化，但即使完全消除搜索耗时，对总训练时间的影响也很小。

## 结果适用范围

本轮已经对齐模型、问题、答案、语料、检索服务、GPU 数量和 Agent 调用上限，
但仍有以下差异：

- NeMo RL 使用结构化 function call；Search-R1 和 ZeroSearch 使用
  `<search>`/`<answer>` 文本标签。
- NeMo RL 使用较新的 Python 3.13、Torch 2.11、vLLM 0.25.1 和 DTensor；
  两套公开项目使用其兼容的 Python 3.10、Torch 2.4、vLLM 0.6.3 和 FSDP
  软件栈。
- Search-R1 和 ZeroSearch 都基于 veRL，它们不是两套完全独立的训练框架。
- 当前只统计了 3 个正式 step，语料也是小规模合成语料。

因此，这份结果适合定位工程瓶颈，不适合直接作为大规模训练速度或模型质量的
最终结论。

## 明天继续的建议顺序

1. 细拆 NeMo RL 的 7.45 秒权重同步，确认时间花在参数打包、传输、vLLM
   refit 还是 worker 串行等待。
2. 尝试减少完整权重同步、并行 fan-out，或将同步与下一步 CPU 准备重叠。
3. 将正式测量扩展到至少 10 个 step，确认 steady-state 均值和长尾。
4. 增加固定生成 token 数的实验，进一步排除轨迹长度对墙钟对比的影响。
5. 如需判断“框架本身”的性能差异，再补一轮尽可能统一 Torch/vLLM 版本的
   对照。
6. 最后换成更真实的数据集和大规模检索语料，验证瓶颈是否发生变化。
